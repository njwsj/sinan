phase7总结-重建 SSE 事件协议和 Redis 回放

一、新增：
	1.events.py
		定义事件名常量
		GenerationEvent：
			to_record：序列化为写入redis的字符串
			from_record：把从redis中的字符串反序列化
			to_sse：转化为sse输出格式
			剩下的是data构造器 例如：event_bus.publish(session_id, events.STEP, events.step_data("analyze", "分析中"))

二、修改：
	1.generation_event_bus.py（基本重写）
		event_key：是list，存事件的完整内容
		seq_key：是存当前的最新序列号
		class EventBus(Protocol): 这个相当于java中的接口 只声明 不实现
		class RedisEventBus: 使用redis实现sse
			a.publish：发布一个事件到redis list中
				1. INCR seq_key → 拿到唯一递增序列号（原子操作，多实例安全）
		        2. 构造 GenerationEvent 对象
		        3. RPUSH event.to_record() → 追加到 List 尾部
		        4. LTRIM → 保持 List 长度不超过 _max_len
		        5. 若是终止事件 → 给两个 key 都打 TTL（晚到客户端仍能拿到 completed）
		    b.replay:一次性读出 cursor 之后的全部历史事件
		    	用于断线重连：客户端带着上次收到的 Last-Event-ID 过来，
        		这里过滤掉已收到的，把剩余事件一次性返回，不丢、不重复。
        	c.subscribe:持续轮询
        		redis.lrange(key, 0, -1)取出所有的redis事件字符串
        		遍历 并反序列化
        			判断传来的游标current和遍历的事件的redis中的数据的seq
        				若seq比current大 就输出
        				若seq比current小 说明 还没遍历到断点的地方 不输出
        class InMemoryEventBus：内存版，开发时可选用

    2.redis.py
    	创建并缓存全局连接池。应用启动时调用一次，重复调用幂等。

    3.generate.py接口
    	传参数增加cursor表示当前游标
    	_stream_generation_events	先回放游标之后的历史事件，再实时订阅；遇终止事件关闭本次连接。

    4.generation_runner.py
    	修改_execute_generation_pipeline方法 主要是将event_bus.publish的调用传参修改

    5.coder.py
    	也是修改相关的event_bus.publish





三、之前的三个必然缺陷：
	
	进程重启事件全丢：	数据只在内存里
		触发场景：
			生成任务跑到一半，服务器 OOM 被系统杀掉
			运维发布新版本，pod/进程重启
			服务崩溃自动重启（supervisor、k8s 的 restartPolicy）
		解决：
			把事件写进 Redis，不放内存。
			publish 的每一条事件都通过 RPUSH 写入 Redis List，进程本身什么都不持有：
			当接收到event为终态时 就将redis中的数据ttl
				Redis 里存的 sinan:generation:events:{session_id} 只是 SSE 推送用的事件历史，里面是 step、code_delta、completed 这些流转状态。真正的生成结果（代码、页面内容）存在数据库里，不在这个 key 里。
				页面内容不依赖 Redis 事件流，用户看到的"生成好的页面"是从数据库读的。事件流的 TTL 只是控制"还能不能用 SSE 回放历史事件"这件事，过期了最多是重连后看不到历史进度，但已生成的结果不受影响。

		由此引出另外一个问题：当进程重启了 在重启的这个过程中 向redis中写数据的过程也终止了，这个event数据存到redis中的意义是？
			答：机器重启过程中 确实redis的写入停止了，Redis 里留的是重启前已经成功写入的那部分事件，比如 seq=1 到 seq=20。
				把event写入redis的价值是：客户端重连后能看到重启前的进度。用户不会看到空白页，能看到"分析完了、设计完了、代码写到一半"的历史状态。
				但是重启期间 seq=21 之后的新事件是空缺的，任务是否能恢复取决于另一套机制。
					靠的是Job + Supervisor（phase6解决的问题）
						进程重启后
						  ↓
						supervisor_loop 启动，每 15 秒扫一次数据库
						  ↓
						list_reclaimable_jobs()：找出 status=running 且 lease_until 已过期的 Job（如果重启后的时间小于lease_until，也会等待自然过期，避免无法区分"进程死了"和"进程还在跑只是重启了"，可能出现两个进程同时跑同一个 Job 的问题。）
						  ↓
						ensure_job_running(job_id)：重新起一个 task 接着跑
						  ↓
						runner 重新执行流水线，新事件继续写入 Redis



	两个客户端互抢事件：	Queue 是消费型的，取走就没了，不能广播
		触发场景：
			用户同时开了两个浏览器 tab 看同一个生成页面
			前端网络抖动，旧连接还没断、新连接已经建立，短暂存在两条 SSE 连接
			你自己开着 debug.html 调试，同时另一个窗口也在跑
		解决：
			LRANGE 读不消耗数据，游标放在每个连接自己的本地变量里。
			current = parse_cursor(cursor)   # 这个 current 是本次连接的局部变量
			while True:
			    rows = await redis.lrange(key, 0, -1)   # 读全部，但不删除
			    for raw in rows or []:
			        event = GenerationEvent.from_record(raw)
			        seq = parse_cursor(event.event_id)
			        if seq > current:
			            current = seq    # 只更新本地游标
			            yield event
			    await asyncio.sleep(self._poll_seconds)

	断线重连没有位置概念：	Queue 没有 cursor，不知道从哪里继续
		触发场景：
			手机用户进了隧道，网络断了几秒
			浏览器 tab 切到后台，系统回收了连接
			Wi-Fi 短暂切换
		解决：
			两阶段恢复（replay + subscribe），游标通过 Last-Event-ID 传递。
			客户端带着 Last-Event-ID: 5 重连
			  ↓
			_resolve_cursor：从 Header 或 query 拿到 cursor="5"
			  ↓
			replay(session_id, cursor="5")：
			    LRANGE 读出全部事件，过滤 seq > 5 的，一次性补发
			  ↓
			subscribe(session_id, last_id="7")： 这里的last_id为7 说明5-7就是我断线时缺失的events
			    从 seq=7 之后开始轮询新事件
			  ↓
			收到 completed → return，关闭连接

四、 job + Supervisor（phase6）和sse重建 + redis回放（phase7）都各自解决了什么问题？又都是怎么解决的？
	
	1.Job + Supervisor：解决"任务能不能跑完"

		问题：生成任务是个耗时很长的后台操作（几十秒到几分钟）。原来直接用 asyncio.create_task 跑，进程一死任务就消失，没人知道它死了，也没人去重跑。

		解决的是任务执行层面的可靠性，核心思路：

		任务不再直接跑，先写入数据库变成一个 Job 记录
		Worker 认领 Job 时写入租约（lease_until = now + 90s），相当于宣告"我在跑"
		心跳每 20 秒续租，只要进程活着租约就一直往后推
		进程死了 → 心跳停 → 90 秒后租约过期 → supervisor 扫描发现 → 重新捡起来跑
		保证的是：任务最终一定会跑完（或达到重试上限），不会因为进程崩溃永久卡死。

	2.SSE 重建 + Redis 回放：解决"客户端能不能看到完整进度"

		问题：任务跑的过程中，客户端通过 SSE 长连接实时接收进度事件。原来用 asyncio.Queue，事件取走即消失，有三个缺陷：进程重启全丢、多客户端互抢、断线重连没有位置概念。

		解决的是事件传输层面的可靠性，核心思路：

		每条事件写入 Redis List，不放内存，不被消费掉
		每条事件有单调递增的 seq，客户端用它做游标
		断线重连时带着 Last-Event-ID，服务端先 replay 补历史，再 subscribe 接实时
		多个客户端各自持有自己的 cursor，LRANGE 只读不删，互不干扰
		保证的是：客户端不管何时连上来、断线多少次，都能看到完整的进度历史。
